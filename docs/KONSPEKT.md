# Конспект: проектная работа по виртуальной инфраструктуре

## 1. Задача проекта

Сервис Kittygram уже состоит из Django API, React, Nginx и PostgreSQL.
В этой дисциплине нужно описать инфраструктуру кодом и связать её с CI/CD,
чтобы сервер создавался воспроизводимо, а приложение автоматически проверялось и выкладывалось.

## 2. Роли инструментов

| Инструмент | Что делает в проекте |
| --- | --- |
| Terraform | Создаёт сеть, подсеть, Security Group, адрес и ВМ через API Yandex Cloud |
| Object Storage | Хранит общий Terraform state между запусками runner |
| cloud-init | При первой загрузке Ubuntu создаёт пользователя и устанавливает Docker/Compose |
| Docker | Запускает компоненты приложения в контейнерах |
| Compose | Связывает контейнеры, сеть, env и постоянные volumes |
| GitHub Actions | Проверяет код, собирает образы, вызывает Terraform и SSH-деплой |
| DockerHub | Хранит опубликованные образы приложения |
| Nginx | Отдаёт React, static/media и проксирует API в Django |

## 3. Terraform: четыре основных команды

- `init`: настраивает backend и устанавливает провайдеры.
- `plan`: сравнивает конфигурацию, state и удалённые ресурсы; показывает будущие изменения.
- `apply`: применяет план. В workflow применяется сохранённый в этом же запуске план.
- `destroy`: удаляет управляемые ресурсы; для этой ВМ это также потеря данных на её диске.

`resource` — объект, которым Terraform управляет. `data` — чтение уже существующего объекта,
например готового образа Ubuntu. `variable` — входной параметр. `output` — результат,
например IP ВМ, который затем использует deployment.
Зависимости по ссылкам на атрибуты позволяют Terraform определить порядок создания ресурсов.

## 4. Зачем state хранится в S3

Runner GitHub Actions временный: локальные файлы пропадут после выполнения job.
Без общего state следующий запуск не узнает, какие объекты уже созданы.
State связывает адреса Terraform-ресурсов с реальными облачными ID.
Он может содержать чувствительные данные и не должен попадать в публичный Git.

Backend-бакет создаётся **до** инициализации основной конфигурации.
Если создавать бакет через Terraform, `bootstrap/` имеет отдельный локальный state, а `infra/` — удалённый.
В фактическом развёртывании бакет заранее создан через S3 API, затем подключён к `infra/`.
Versioning позволяет восстановить предыдущую версию state, но не заменяет блокировку конкурентных изменений.
В учебном решении workflow сериализуются через общую concurrency group; параллельный локальный apply запрещён процессом.
State не является резервной копией PostgreSQL и фотографий.

## 5. Сеть и доступ

VPC объединяет ресурсы сети, подсеть задаёт диапазон частных адресов и зону.
У ВМ есть внутренний IP, а статический внешний IPv4 нужен пользователям и GitHub runner.
Security Group пропускает входящие SSH22 и HTTP9000, остальные входящие соединения не разрешены.
Все исходящие соединения нужны для репозиториев пакетов, DockerHub и внешних API.
PostgreSQL5432 и Gunicorn8000 доступны внутри Compose-сети, но не опубликованы на интерфейс ВМ.

SSH использует две разные пары ключей: пользовательская доказывает право входа,
а ключ сервера подтверждает, что подключение идёт к нужной машине.
Публичный ключ сервера проверяется через доверенную консоль YC и сохраняется в known_hosts.

## 6. cloud-init

`user-data` передаётся в metadata ВМ. Ubuntu читает cloud-config при первом старте.
Скрипт создаёт `deploy`, запрещает парольный SSH и устанавливает Docker с Compose plugin.
Terraform может завершить создание ВМ раньше установки пакетов, поэтому deployment ждёт `cloud-init status --wait`.
`apt` может быть занят обновлениями: используется ожидание блокировки, её файл не удаляется.
Обычная перезагрузка не означает повторное выполнение всех первоначальных действий cloud-init.

## 7. CI/CD

CI: PEP8, тесты backend с настоящим PostgreSQL на runner, тест frontend, Terraform validate и структура файлов.
CD: сборка трёх образов, push в DockerHub, получение IP из state, SSH, Compose, проверка URL и Telegram.
Тег SHA связывает запущенные образы с конкретным коммитом; `latest` оставлен для совместимости с заданием.
Secrets содержат ключи и пароли, Variables — обычные параметры проекта.

Готовность БД подтверждает healthcheck, после него выполняются миграции.
Статика React заново копируется из образа при каждом деплое: один только volume не обновляет старую сборку.
Django `collectstatic` складывает файлы admin/DRF в volume, который Nginx читает.
База и media сохраняются в volumes между пересозданиями контейнеров на одной ВМ.

## 8. Функциональные проверки

Гость не получает список котов. Пользователь может зарегистрироваться, войти, добавить кота,
изменить или удалить своего кота, загрузить фото, выбрать достижения. Чужого кота можно только смотреть.
На странице не более десяти котов. Автотесты прав доступа нужны даже тогда,
когда интерфейс скрывает кнопки: API обязан самостоятельно проверять владельца.

## 9. Что объяснить ревьюеру

- Где создаётся бакет и почему он отделён от основной инфраструктуры.
- Как следующий runner находит созданную ВМ через state.
- Почему наружу открыты только два порта.
- Как автоматически устанавливаются Docker и Compose.
- Как deployment узнаёт реальный IP и проверяет SSH-сервер.
- Чем успешный `terraform apply` отличается от успешной проверки приложения.
- Где лежат данные и что произойдёт при уничтожении ВМ.
- Как результаты тестов подтверждают работоспособность, а не только наличие YAML-файлов.
